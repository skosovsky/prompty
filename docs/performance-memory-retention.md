# Cache retention and capacity contract

`WithCache(base prompty.Registry, ttl time.Duration) *CachedRegistry` remains unbounded: cardinality never evicts a fresh entry. `WithCacheLimit(base prompty.Registry, ttl time.Duration, maxEntries int) *CachedRegistry` opts into a positive entry limit. Both constructors panic with `remoteregistry: base registry must not be nil` for a nil base; the limited constructor checks base first, then panics with `remoteregistry: maxEntries must be positive` for zero or negative limits.

The limited cache uses FIFO publication order. A successful fetch appends its generation; hits do not move it or extend TTL. Refresh/replacement removes the old generation and appends the successful new one. Before publication, expiration cleanup removes expired entries; if capacity remains full, publication evicts the oldest retained generation. Admission and eviction occur atomically under the cache mutex. Failed/canceled fetches never evict a fresh entry to make room. This policy preserves a cheap shared-lock hit path without LRU writes on each read. The hit path captures the entry pointer and deadline values under the read lock, then compares those copies outside the lock; concurrent eviction does not invalidate the already captured generation. The maintenance path reacquires the write lock and rechecks time/membership. It is an implementation policy chosen for this API, not an inferred user agreement about FIFO.

TTL determines freshness. Positive-TTL generations expire at publication time plus TTL; equality with the deadline is expired. Material lookups (including hits) and successful attached fetch publication drain all expired generations. A fixed TTL makes publication order also expiration order, so an intrusive FIFO list supplies both indexes: no-expiration checks and capacity victim selection are O(1), and cleanup is O(k) for k expired generations. Removing an arbitrary entry is O(1). Each retained entry has one embedded list node; removal clears its links, so refresh/eviction churn leaves no stale index nodes. Empty cleanup resets the map and list to release backing storage; partial removals clear payload references while the map may retain backing capacity. `EvictAll` immediately replaces maps and clears both list endpoints.

There is no timer or maintenance goroutine. An idle cache may retain expired entries until its next material lookup or explicit eviction. Canceled lookups rejected before acquiring the lock and delegated introspection operations do not trigger cleanup. TTL <= 0 keeps generations fresh indefinitely; `WithCache` retains them until explicit eviction. With `WithCacheLimit`, capacity can still evict such a generation, and a later fetch may capture a different source generation.

The limit bounds only cache-owned stored entries, not bytes, caller-held plans/snapshots, distinct in-flight fetches, or source work. Already returned generations remain valid after eviction. Existing waiters can receive a successfully fetched generation even when explicit eviction detached its fetch or another capacity publication immediately evicted it. Detached fetch completion never republishes its result or replaces a newer in-flight generation. Remote fetches and user callbacks run outside the cache mutex. Expired fetch errors never fall back to the expired generation; singleflight and independent waiter cancellation remain unchanged.
