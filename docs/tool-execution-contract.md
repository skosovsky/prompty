# Tool execution contract

`ToolScope` is a caller-owned declaration for local tools, separate from authorization. No additional scope leaves `PromptExecution.Tools` as the execution boundary. A bound scope with empty `Allowed` permits no local tools. `RenderPlan.WithToolScope` binds before materialization; `PromptExecution.WithToolScope` binds directly and returns a validated clone. `execution.ToolScope()` returns a copy. The internal snapshot survives execution clones, history/message additions and wire restore. Caller changes to definitions are checked again before checked provider dispatch and core text/structured/stream helper dispatch, context-window/tracing delegation and one-shot handler invocation. Hosted provider tools remain outside local registry dispatch.

Names must be nonempty and unique. Required and forced tools must have definitions in the execution. Every definition in a bound scope must have an Allowed entry with the same exact structural JSON schema and normalized dialect. Its declared capabilities must be included in that entry. Scope Required entries must also be present and satisfy their schema/dialect/capability requirements. Empty definition parameters are not a wildcard matching a different Allowed schema. These declarations are not authenticated policies: a host accepting untrusted wire input must apply its own authorization and binding policy.

Execution wire uses `prompty.execution.v2`. A present `tool_scope` includes `allowed` and `required` arrays; absent scope preserves direct unscoped execution. The old `prompty.execution` marker is rejected. Recipe checkpoints still describe a recipe: runtime scope is explicitly supplied through `BindRuntime` and is retained by the materialized execution. There is no agent-run checkpoint or IAM backend.

Tool handlers receive `context.Context`: `ToolHandler.Handle(ctx, args)`, `NewTypedTool(name, func(ctx, args) (result, error))`, `TypedTool.Invoke(ctx, json)`, and `ToolInvoker.InvokeTool(ctx, name, json)`. Update callers directly. A registry can serve concurrent calls after registration has completed; it does not store a context or launch handler goroutines. Pass the context to HTTP/DB operations. Cancellation is cooperative and cannot roll back a completed side effect.

`ExecuteWithTypedTools` performs one model call. It validates the complete batch against original execution schemas, scope, correlation and registry decoding before any handler. The model sees a clone and cannot expand the retained boundary by mutating its argument. Cancellation is checked before model dispatch, before each handler and after each handler. Later calls do not start after cancellation. No retries, compensation or scheduler are built in.

A failed model call may return a known response. `ToolDispatchError.Response` retains a clone for host reconciliation while `errors.Is` still exposes the transport or context cause; none of its tool calls are executed. Batch-validation errors retain the response in `ToolCallError.Response`. Results from handlers returning both data and an error remain in the returned tool messages. `IsError` marks an invocation error, including cancellation; it does not imply the side effect was undone. If no data is available, the result message contains the error text. A canceled last handler cannot return success from the one-shot helper, and completed results remain available. Joined errors retain both cancellation and underlying handler causes.

Caller-supplied schema compilers receive isolated source documents at tool/structured helper boundaries. Sources are read-only: a detected contract change during successful compilation is rejected before dispatch. This prevents compiler normalization callbacks from altering a previously checked execution scope. Cancellation before structured-stream dispatch returns its cause without constructing a downstream source handle.
