# High-level helpers and the Invoker boundary

Core accepts an application-owned `Invoker`; it does not discover that implementation's SDK, endpoint configuration or capability knowledge. An implementation must establish execution guarantees before dispatch or fail closed. Interface conformance alone does not attest to truthful provider behavior. This is a host-port obligation, like truthful validator and capture-sink implementations, not IAM or a permission system.

Use `adapter.NewClient` or `adapter.NewRuntimeClient` for library-owned provider execution. Their sync, native and buffered paths use shared `Prepare`, which performs effective-profile validation, actual mapping-port checks, state/capture/cache/schema preparation before transport dispatch. A custom wrapper can delegate unchanged executions to these clients without exposing descriptors through the core interface. Do not delegate to raw SDK `Execute` and advertise the result as checked invocation. Do not clear requirements, supply invented diagnostics or silently change stream mode.

Core helpers independently validate original schemas, canonical metadata/outcomes and entire tool batches before handlers. They do not reimplement provider mapping or transport preflight. A fabricated custom invoker can ignore its contract; a post-response check cannot retroactively provide a zero-dispatch guarantee. No such claim is made here. The independent completeness audit reconciled S04-04 against the original task: shared preparation for library-owned execution and preservation through wrappers fulfill the requirement. A separate proof-bearing port for arbitrary host implementations is neither required nor a transport attestation.

`adapter/helper_preflight_conformance_test.go` provides thirty permanent AAA fixtures: five helper paths × both checked clients × three preflight rejections, behind a wrapper exposing only the two Invoker methods. Paths are structured sync, typed tools, tool validation, structured native and structured buffered. Rejections are unknown extension capability, unsupported output MIME and unknown required block cache. Every case checks the typed error, zero Translate, zero provider calls and unchanged original execution wire. This verifies composition and preservation of requirements, not every provider guarantee or an arbitrary implementation's truthfulness. Other state/capture/schema/native fixtures remain separately authoritative.

These tests use local checked fixtures, not live endpoints. They do not resolve remote-operation, cache-resource, extra native-adapter or forced-tool-output triggers. Final independent audits still have to validate the original scope and this boundary decision.
